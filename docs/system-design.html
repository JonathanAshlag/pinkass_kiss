Big picture

Documents live in a virtual filesystem (folders and files) stored in Postgres. Each file is Markdown plus metadata (title, tags, status, sources...), inspired by Google's Open Knowledge Format. Data comes in through ingestion, lives in storage with a derived semantic index beside it, and goes out through one service layer to the REST API and to agents.

Part 1: Ingestion (file upload)

POST /ingest takes a multipart upload (files[] with parallel paths[]), mirrors the folder tree into the KB, converts each file to Markdown, indexes it, and keeps the original. The caller either gets everything or nothing.

The three places a file must reach

Postgres files

The canonical record: a files row with the converted Markdown content, metadata, and blob_key / checksum of the original. Its commit is the one commit point.

pgvector kb_chunks

The derived semantic index: embeddings of 1500-char chunks of the body, with heading and line range per chunk. A record manager tracks what is indexed.

S3 originals/<file id>

The raw original (the PDF, DOCX...) so it can be downloaded later via GET /nodes/{id}/raw. Not kept for plain Markdown.

Postgres is the source of truth. The other two can be rebuilt or are only reachable through a committed row. The catch: pgvector's store and S3 cannot join a Postgres transaction.

Upload flow

1

Receive and validate

Stream files (1 MiB chunks) into a temp dir mirroring the tree. Check paths (relative, no .., no case-insensitive duplicates) and size limits (413 if exceeded).

ingest/upload.py: ingest_upload
↓
2

Plan and convert cpu

Walk the tree, run each file through its processor, build a FolderPlan. Heavy conversions run in a shared process pool. If any file fails, nothing happens (IngestFailed, 422, lists every failure).

ingest/folder.py, ingest/convert.py
↓
3

Stage before commit pgvector s3

Embed all chunks and add them to pgvector; upload originals to S3 in parallel. Nothing in Postgres yet, so nothing can see these.

service.stage_before_commit
↓
4

Materialize rows postgres

Create folder and file rows through the service (permission checks apply).

ingest/plan.py: materialize
↓
5

Commit the commit point

A before_commit hook re-checks the index (already-staged chunks are skipped, never re-embedded). The DB commit is when the upload becomes real.

service.commit
↓
6

Settle

After the transaction ends: on commit, clean stale chunks; on rollback, remove staged chunks and uploaded originals that no committed row references.

after_transaction_end hook, indexer.reconcile

The all-or-nothing mechanism

A write lands in Postgres, pgvector and S3 together, or leaves no reachable trace in any of them.

A true distributed transaction is impossible here (LangChain's PGVectorStore and SQLRecordManager commit on their own connections; S3 has no transactions). So we use one commit point and stage-then-settle:

  1. Stage before the commit. Chunks go into pgvector and originals into S3 first. They are invisible: search only returns chunks whose file_id belongs to a committed row, and only a committed row points at an S3 key.
  2. Commit in Postgres. This is the only moment that matters.
  3. Settle after. A state-based cleanup compares what was staged to what is committed. Committed: drop stale chunks of edited/deleted files. Rolled back: drop the staged chunks and orphan originals.

Because settling looks at the actual state rather than "did the commit succeed", it is correct even when the connection dies mid-COMMIT and the outcome is unknown. Failures at any stage (embedding server down, S3 error, DB lock timeout) undo what was staged and return an error (indexing failure is 503, nothing written; S3 failure 502).

Crash backstop: if the process is killed between staging and settling, scripts/gc.py deletes originals and chunk groups older than 24 h that have no files row. Correctness never depends on it. Read-time validation also drops any hit whose chunk no longer matches the file's current text.

Efficiency improvements made to the flow

  • Parallel conversion. PDF/Docling work runs in a shared process pool (default min(4, CPUs)); a dead worker fails only its pending files and the pool is rebuilt. Measured: 3.4 pages/s with 1 worker, 7.7 with 4.
  • Embed once. Chunks are staged before the commit and the commit-time hook finds them already recorded, so nothing is embedded twice. Unchanged chunks of an edited file are skipped as well (incremental cleanup).
  • Batched staging. Add-only indexing across files in batches of 128, and 32 inputs per embeddings request. This works well with batching servers (TEI/vLLM).
  • One batch per file when re-indexing. A file split over several batches had its later chunks deleted and re-embedded on every run; one batch per file fixed that.
  • Parallel, streamed S3 uploads (8 threads, SHA-256 checked by S3, never read whole into memory), with timeouts and retries.
  • Plan first, write later. Conversion and validation happen before any network or DB write, so a bad file fails fast and cheaply.
  • Retag does not re-embed. Only the body is embedded, not the frontmatter.
  • Deferred File.content in the ORM, so listing and agent tools stop loading every file's text.
  • OpenAI-compatible embeddings (TEI, vLLM) so production can use a GPU server instead of a single-request Ollama.

Increasing capacity with the current setup

An upload is synchronous inside one HTTP request, and its steps run one after another, so throughput is set by the slowest shared resource: conversion CPU in the API pod, the embedding server, or pgvector write speed on Postgres (about 2 min per 4,500 chunks, mostly HNSW maintenance). The cheap wins are to run embeddings on a GPU server (TEI/vLLM) which batches concurrent requests, set KB_INGEST_WORKERS to about pod cores ÷ 1.6, scale API replicas (each has its own pool, DB pool size and conversion workers) and give Postgres more CPU. The structural next step is moving big uploads into an async ingest job with a status route (still all or nothing), which removes the router timeout and lets a queue throttle work to what the shared services can take.

Part 2: Agent consumption

An agent gets AgentTools(manifest_id). The manifest is its scope: the agent only sees files inside it, and paths are shown relative to that scope. Each call opens its own session. Errors come back as an error: ... string so the model can recover instead of crashing the run. Output is capped (max_chars) with a [truncated ...] hint on how to narrow the call.

The idea (from the DCI paper in docs/reference) is to let agents navigate the corpus like a developer navigates a repo: ls, grep, sed. Agents never see a "virtual file" differently from what is stored: it is the YAML-ish frontmatter (one key: JSON per set field) followed by the Markdown body, and every tool counts lines on that same text.

The tools and what they return

1. list_paths(under=None, recursive=False) like ls / find

Top-level of the manifest, or the children of under. One line per node: folders end with /; files show status; description when set.

papers/qasper-1234/  Neural MT for low-resource languages
papers/qasper-1234/00-overview.md  [stable]  Title, abstract and outline
papers/qasper-1234/01-introduction.md  [stable]
papers/qasper-1234/metadata.md  [stable]

2. search_lines(pattern, ignore_case=True, files_only=False) like grep -n

Regex per line over all files in scope. Hits are path:line:text; with context, neighbouring lines use - and groups are separated by --. files_only returns just the matching paths, a cheap first step. Several patterns on one line means all must match (grep a | grep b).

papers/qasper-1234/04-results.md:12:BLEU improved from 21.3 to 24.8 on the test set
papers/qasper-1234/05-conclusion.md:3:We report BLEU gains on all language pairs

No hits: (no matches). Bad regex: error: invalid pattern: ....

3. read_lines(path, offset=1, limit=50) like sed -n

One file, a line range, each line prefixed by its number and a tab, under a header with the range and total. Line numbers are the same as in search_lines output, so a hit is expanded with offset=hit-k.

papers/qasper-1234/04-results.md (lines 10-13 of 87)
10	### Main results
11
12	BLEU improved from 21.3 to 24.8 on the test set
13	...

4. semantic_search(query, k=5) optional, by meaning

For conceptual questions where the exact words are unknown. Embeds the query, searches pgvector, filtered to files in the manifest (file_id IN ...). Each hit is a chunk: path:start-end [heading] (similarity) plus a snippet. The line range plugs straight into read_lines.

papers/qasper-1234/03-method.md:40-71 [Method > Data] (0.82)
    We train on 1.2M sentence pairs collected from ...
-- read a hit in full with read_lines(path, offset=start_line)

If the embeddings backend is down the tool says so and suggests search_lines.

search_lines: the regex runs in Postgres

Earlier, search loaded every file's text into Python and ran re on it. Now it is one SQL query per call and no user regex ever runs in the Python process.

Why, and the trade-offs

  • Data stays put. Only matches cross the wire, not the whole corpus; the bigger the corpus the bigger the win.
  • Safety. The query runs in a savepoint with a local statement_timeout of 5 s (then restored). Timeout (57014) becomes pattern too slow; bad syntax becomes invalid pattern. A runaway regex can't hang the API process.
  • Dialect is POSIX ARE, not Python re. The word boundary is \y (\b is a backspace in ARE and would silently match nothing, so it is rejected). No named groups, no mid-pattern (?i); use ignore_case. The tool description tells the model.
  • Case folding and \w follow the database locale, so the DB must be UTF-8 (not C); Hebrew text is covered by a test. Needs PG 14+.

Other notable details

  • Permissions. Skeleton folders can't be renamed/moved/deleted, auto-updated ones are fully locked, and agent_locked blocks agent writes. Agents have no write tools yet.
  • No version history, soft delete only. Deleting a folder soft-deletes its subtree; restore is per node. These were deliberate choices.
  • Folders hold no content. Text describing a folder goes in a child file.
  • Advisory OKF checks never block writes: broken db://files/<id> links, frontmatter shape, unresolved footnotes, staleness. They show up as warnings on single-node responses.
  • Title is the filename stem for every ingested file (no heading parsing); code and config files are intentionally not ingested.
  • Evaluation. A LangGraph agent over these tools is graded by an LLM judge on a 20-paper QASPER fixture, to measure whether tools and semantic search earn their place.
  • Settings live in one place (kb.settings); python -m kb.settings prints the effective values.
  • Known gaps: authn (the actor is just "human" or "agent"), synchronous big uploads, no purge of originals for deleted files, no per-file converter timeout.
