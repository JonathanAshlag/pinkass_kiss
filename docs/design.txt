  <h1>pinkass_kiss: a lean knowledge base that serves context to agents</h1>
  <p class="lede">Markdown files with OKF-style frontmatter, kept in a Postgres virtual filesystem. Every read and write passes through one service layer. A pgvector index is derived from the files, and agents explore the corpus with bounded <code>ls</code> / <code>grep</code> / <code>read</code> tools scoped to a manifest.</p>

  <div class="sec-head"><span class="sec-num">00</span><h2>System at a glance</h2></div>

<section id="trajectory">
  <div class="sec-head"><span class="sec-num">01</span><h2>A document's trajectory</h2></div>
  <p>Follow one upload, a folder <code>handbook/</code> holding <code>setup.md</code> and <code>policy.pdf</code>, from the browser to a searchable chunk. The whole ingest is a single database transaction: it either lands completely or not at all.</p>

  <div class="board">
    <ol class="pipeline">
      <li>
        <h4>Pick a folder in the UI</h4>
        <div class="where">static/index.html · GET /ingest/extensions</div>
        <p>The dev UI uses <code>&lt;input webkitdirectory&gt;</code>. It asks the API which extensions have a processor and drops hidden and unsupported files on the client, so they are never uploaded.</p>
      </li>
      <li>
        <h4>Multipart upload</h4>
        <div class="where">POST /ingest <span class="tag io">HTTP</span></div>
        <p>The request carries <code>files[]</code> plus a parallel <code>paths[]</code> (relative paths, because multipart filenames lose directories), an optional <code>parent_id</code> and <code>tags[]</code>. A count mismatch is a 422.</p>
      </li>
      <li>
        <h4>Validate and stage on disk</h4>
        <div class="where">kb.ingest.upload.ingest_upload <span class="tag io">temp dir</span></div>
        <ul>
          <li>Paths must be relative, <code>/</code>-separated, free of <code>..</code>, and all under one top-level folder. Anything else raises <code>UploadError</code> (422).</li>
          <li>Bytes are written into a temp dir that mirrors the tree, so processors stay path-based.</li>
          <li>Each source is recorded as <code>upload:&lt;rel path&gt;</code>, not the temp path.</li>
        </ul>
      </li>
      <li>
        <h4>Plan: walk and convert, without touching the DB</h4>
        <div class="where">kb.ingest.folder.plan_folder → processors registry</div>
        <ul>
          <li>Hidden entries and symlinks are ignored. The processor is chosen by lowercase extension.</li>
          <li><b>Markdown</b> (<code>MarkdownProcessor</code>): content is stored verbatim with no frontmatter parsing. The title is the filename stem (for every format).</li>
          <li><b>PDF</b> (<code>LoaderProcessor</code> + <code>PyMuPDF4LLMLoader</code>, or Docling when installed, which also covers .docx/.pptx/.html) is converted to markdown. Empty output counts as a failure.</li>
          <li>Unsupported files go to <code>report.skipped</code> and processor errors to <code>report.failed</code>. Both are per file and never fatal.</li>
          <li>The result is a <code>FolderPlan</code> of <code>PlannedNode(path, type, title, content, fields)</code>.</li>
        </ul>
      </li>
      <li>
        <h4>Keep the raw original (converted formats only)</h4>
        <div class="where">kb.storage.blobs.put_original <span class="tag io">S3 / local</span></div>
        <p>For processors with <code>retain_original</code> (the PDF loader, not markdown), the source bytes are stored content-addressed at <code>sha256/&lt;hex&gt;</code> in S3 (<code>BLOB_BUCKET</code>). The plan gets <code>blob_key</code>, <code>blob_size_bytes</code>, <code>blob_mime_type</code> and <code>blob_checksum</code>. Blobs are written before the DB commit, so a rollback can leave a harmless, deduplicated orphan.</p>
      </li>
      <li>
        <h4>Materialize: plan becomes nodes</h4>
        <div class="where">kb.ingest.plan.materialize → service.create_folder / create_file <span class="tag db">INSERT</span></div>
        <ul>
          <li>The root becomes a folder (title = top-level dir name). Ancestor directories the plan implies are created as plain folders only when something below them is created, so empty dirs get no node.</li>
          <li>Every create goes through the service as actor <code>human</code>, so the policy runs a <code>CREATE_INSIDE</code> check on each parent.</li>
          <li>The service records each new id in <code>session.info</code> as a touched id.</li>
          <li>Postgres assigns ids with <code>gen_random_uuid()</code>. The file id doubles as the OKF frontmatter <code>id</code>.</li>
        </ul>
      </li>
      <li>
        <h4>Commit</h4>
        <div class="where">service.commit(session, schedule=BackgroundTasks.add_task) <span class="tag db">COMMIT</span></div>
        <p>One transaction for the whole folder. If it fails, nothing is created and the touched set is cleared. If it succeeds, the touched ids are handed to the indexer as a background task, and the HTTP response returns an <code>IngestReport</code> (root id, created ids, skipped, failed).</p>
      </li>
      <li>
        <h4>Index (after the response)</h4>
        <div class="where">semantic_index.indexer.index_files <span class="tag async">background</span></div>
        <ul>
          <li><code>FileNodeLoader</code> reads each active file in its own session.</li>
          <li>The markdown body is split with <code>RecursiveCharacterTextSplitter</code> (markdown, 1500 chars / 200 overlap). Each chunk gets its heading path and virtual-file line range.</li>
          <li>The text is embedded as <code>"&lt;title&gt; &gt; &lt;heading&gt;"</code> + chunk via Ollama <code>nomic-embed-text</code> (768d) and stored in <code>kb_chunks</code>.</li>
        </ul>
      </li>
    </ol>
  </div>

  <h3>Where it ends up</h3>
  <p>After the upload, the two documents live in three places. Matching coloured keys mark the same value appearing in more than one table: that is how the stores point at each other.</p>

  <div class="estate">
    <div class="zone zone-pg">
      <div class="zone-head">
        <span class="zone-kind">Postgres</span>
        <span class="zone-sub">database <code>pinkas</code> · one instance holds both the canonical tables and the vector index</span>

  <h3>The virtual file: one rendering, shared line numbers</h3>
  <p>Agents never see raw columns. <code>kb.okf.render_virtual_file</code> renders each file as a frontmatter block (one <code>key: &lt;JSON&gt;</code> line per set field) followed by the body. <pre><span class="c"> 1</span>  ---
<span class="c"> 2</span>  <span class="h">id:</span> "3f9c…"
<span class="c"> 3</span>  <span class="h">type:</span> "file"

  <h3>The mechanisms that keep it complete</h3>
  <div class="grid2">
    <div class="card"><div class="k">1 · single write seam</div><p>Every mutation goes through <code>kb.service</code>, which records touched ids. Delete also records every descendant its cascade soft-deletes, so a folder delete unindexes the whole subtree.</p></div>
    <div class="card"><div class="k">2 · commit before index</div><p>The indexer runs strictly after <code>COMMIT</code>, in its own session, so it always reads committed state. A failed commit or a rollback clears the touched set, so a write that never happened is never indexed.</p></div>
    <div class="card"><div class="k">3 · ids, not events</div><p><code>index_files</code> takes any id and reconciles it. Active with content: index. Soft-deleted, missing, folder or blank: unindex. Reprocessing an id is always safe, so over-indexing costs nothing but time.</p></div>
    <div class="card"><div class="k">4 · content hashes</div><p>LangChain's <code>SQLRecordManager</code> stores a hash per chunk. With <code>cleanup="incremental"</code>, unchanged chunks are skipped, new ones embedded, and stale ones for that file deleted.</p></div>
    <div class="card"><div class="k">5 · one batch per file</div><p>Each file is indexed as a single batch (<code>batch_size=len(chunks)</code>). Incremental cleanup runs after every batch, so splitting a file across batches used to delete and re-embed its later chunks on every run. A regression test covers a 162-chunk file.</p></div>
    <div class="card"><div class="k">6 · per-file isolation</div><p>A failure on one file is caught and listed in <code>IndexResult.failed</code>. The other files in the batch are still indexed.</p></div>
    <div class="card"><div class="k">7 · DB-level backstop</div><p><code>kb_chunks.file_id</code> references <code>files</code> with <code>ON DELETE CASCADE</code>, so a hard delete can never leave orphan chunks pointing at a missing file.</p></div>
    <div class="card"><div class="k">8 · full rebuild</div><p><code>reindex_all()</code> (<code>POST /index/reindex</code>, <code>scripts/reindex.py --all</code>) re-indexes every active file with full cleanup, removing any chunk this run did not confirm. A second run on an unchanged corpus skips everything.</p></div>
  </div>

  <h3>Scope is applied at query time, not stored on chunks</h3>
  <p>Chunks hold only <code>file_id</code>, heading and line range. Paths, tags, status and manifest membership are resolved when a search runs and passed as a <code>file_id $in [...]</code> filter. Moves, retags and manifest edits therefore cannot leave the index out of date, because there is nothing about them in the index. Searches set <code>hnsw.iterative_scan=relaxed_order</code> so a narrow filter still returns <i>k</i> hits.</p>

  <h3>Where a document can still go missing today</h3>
  <p>The design repairs drift but does not yet detect it. These are the known gaps:</p>
  <div class="grid2">
    <div class="card gap"><div class="k">process dies after commit</div><p>The index task is an in-process <code>BackgroundTask</code>. If the server stops between commit and indexing, those ids are lost. Nothing is persisted to retry from.</p></div>
    <div class="card gap"><div class="k">embeddings server down</div><p>Failures are logged, never raised, and never retried. The write succeeds and the file stays unindexed until the next edit or a reindex.</p></div>
    <div class="card gap"><div class="k">bypassing the seam</div><p>Code that calls <code>session.commit()</code> directly, or runs with <code>KB_AUTO_INDEX=0</code>, commits without indexing.</p></div>
    <div class="card gap"><div class="k">no drift detector</div><p>There is no index-status route that compares <code>files.updated_at</code> against the record manager, so drift is only fixed when someone runs a reindex.</p></div>
  </div>
  <div class="callout">
    <p><b>Suggested closure:</b> write touched ids to an outbox table inside the same transaction and have a worker drain it with retries. Add a periodic reconcile that diffs active file ids and content hashes against <code>upsertion_record</code>, exposed as an index-status route. Both reuse <code>index_files</code> unchanged, since it already accepts any id.</p>
  </div>
</section>

<section id="permissions">
  <div class="sec-head"><span class="sec-num">03</span><h2>Permissions</h2></div>
  <p>Rules live in <code>kb.policy</code>, a pure module with no session and no I/O. The service loads the node and its ancestors (nearest first) and calls <code>check(actor, action, node, ancestors)</code> before every mutation. A denial raises <code>PermissionDenied</code>, which the API maps to <b>403</b>. Reads are never restricted. There is no authentication yet: the actor is the string <code>"human"</code> or <code>"agent"</code>, and the API always uses <code>"human"</code>.</p>

  <p>Agents don't get a retriever that picks passages for them.   <h3>Design rules every tool follows</h3>
  <div class="grid2">
    <div class="card"><div class="k">manifest is the boundary</div><p>Every call resolves the manifest to its node set first (folder members expand to their live subtree). A path outside it does not exist for the agent: <code>no such path in manifest</code>.</p></div>
    <div class="card"><div class="k">paths are derived</div><p>Paths are <code>/</code>-joined titles from the KB root, computed at read time and never stored. Sibling title collisions get a <code>~&lt;8 hex of id&gt;</code> suffix. A raw uuid works anywhere a path does.</p></div>
    <div class="card"><div class="k">bounded output</div><p>Every result is capped at 20,000 chars (max 50,000), cut at a line boundary with a <code>[truncated … — hint]</code> note that tells the model how to narrow the call.</p></div>
    <div class="card"><div class="k">errors are text</div><p>A bad path, invalid regex or out-of-range argument returns <code>error: …</code> instead of raising, so the model can correct itself. If the index is down, <code>semantic_search</code> says so and points the model to <code>search_lines</code>.</p></div>
    <div class="card"><div class="k">one coordinate system</div><p>Grep line numbers, <code>read_lines</code> offsets and semantic hit ranges all refer to the same virtual file, so any hit can be opened directly with <code>read_lines(path, offset=start_line)</code>.</p></div>
    <div class="card"><div class="k">read-only, self-contained</div><p>Each call opens and closes its own session, so a tool object can outlive a transaction and run on the framework's threads. There are no write tools.</p></div>
  </div>

  <h3>Also reachable over HTTP</h3>
  <p>The same service functions back <code>GET /manifests/{id}/paths</code>, <code>/search</code>, <code>/read</code> and <code>/semantic</code>, so an external agent runtime can use the tools without importing Python. The underlying DCI functions accept more than the agent wrapper exposes: several AND-ed patterns, <code>paths</code> restriction and <code>context</code> lines for search. Widening the agent signatures is a one-line change in <code>agent_tools.py</code>. The tool docstrings there are what the model reads, so tune tool wording there.</p>

  <h3>Evaluation</h3>
  <p>QASPER papers are loaded as one folder per paper mirroring its outline (numbered section files, <code>figures/</code>, <code>tables/</code>, a <code>00-overview.md</code>), with <code>role:*</code> tags on sections. <code>tests/eval/test_qasper_llm.py</code> runs a LangGraph agent bound to these tools and scores Answer-F1. Setting <code>QASPER_SEMANTIC=1</code> adds <code>semantic_search</code>, so the eval can show whether the vector index improves answers over grep and read alone. That comparison has not been run yet.</p>
