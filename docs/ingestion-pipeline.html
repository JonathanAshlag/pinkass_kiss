File ingestion pipeline

1. The guarantee

A write, whether a whole folder upload or a single PATCH, either lands in all three stores or leaves no reachable trace in any of them:

StoreWhat it holdsWritten by
Postgres dbfolders / files rows (the canonical data)our SQLAlchemy session
pgvector indexkb_chunks (embeddings) + upsertion_record (LangChain's record manager)LangChain index(), PGVectorStore, SQLRecordManager
S3 s3raw originals of converted files (PDF, DOCX, ...) under originals/<file id>BlobStore.put_original (boto3)

The atomic unit is the whole request: if one file of a 300-file upload fails to convert, nothing from the upload is written anywhere, and the error lists every failed file so they can all be fixed at once.

2. Why one commit point, not one transaction

The three stores can't share a transaction. PGVectorStore checks out its own (async) connection and commits on it for every call, and SQLRecordManager commits inside its own sessions; neither accepts an external transaction. S3 has no transactions at all. Replacing LangChain's indexing machinery with hand-written SQL was rejected, so the design keeps it and uses a saga with a single commit point:

  • The DB commit is the moment the write happens.
  • Chunks and S3 objects are written before it, in places nothing can reach until the rows exist.
  • After the transaction ends, everything is settled: kept and tidied after a commit, undone after a rollback.

To make that possible, migration 0003 dropped the foreign key from kb_chunks.file_id to files: chunks have to be insertable before their file row commits, from LangChain's own connection.

3. The flow, step by step

For POST /ingest (and scripts/ingest_folder.py, ingest_git.py). Cheapest and likeliest failures run first, so most failures happen before anything needs undoing.

1

Validate and spool the upload

Paths must be relative, without .., under one top folder or all loose; no case-insensitive duplicates; size and count limits are checked while streaming. Files are mirrored into a temp dir. Nothing written yet.

kb/ingest/upload.py · ingest_upload → UploadError 422 / UploadTooLarge 413
↓
2

Plan: walk and convert cpu

Walk the tree (hidden entries and symlinks ignored, unsupported extensions skipped). Convert every file: PDFs and Office files run in a shared process pool, markdown/text in-process. Every file gets its UUID up front; converted files also get an Original (path, MIME, size, SHA-256, hashed locally). No DB, no network.

kb/ingest/folder.py · plan_folder, kb/ingest/convert.py · convert_all
↓
3

Any conversion failed? Stop.

IngestFailed with every (path, error). Nothing has been embedded, uploaded or written, so there is nothing to undo.

IngestFailed → 422 {detail, failed: [{path, error}]}
↓
4

Stage the index index

Build LangChain Documents from transient File objects (final ids and fields, not in the DB yet), split into chunks and run index(cleanup=None, batch_size=128): add-only, embeds and inserts, deletes nothing. The ids are recorded as "touched/created" first, so even a half-done staging is undone by id.

kb/service.py · stage → _stage_index → indexer.stage_documents · IndexingError 503
↓
5

Upload originals s3

8 parallel PutObjects, streamed from the temp dir, with ChecksumSHA256 so S3 rejects corrupted bytes. Every key that made it is recorded for the undo. On failure, stage undoes its own chunks and uploads, then raises.

service._upload_originals · BlobStore.put_original · BlobStoreError 502
↓
6

Materialize rows db

Create folders and files (with the pre-chosen ids and blob_* columns) inside the session's transaction, with the usual permission checks. Uncommitted.

kb/ingest/plan.py · materialize → service.create_file / create_folder
↓
7

before_commit: stage what the transaction touched

Flush, load the active touched files and run the same add-only index(). For an ingest every chunk is already in the record manager, so all are skipped (no second embedding). For a PATCH this is where the embedding happens. Failure raises IndexingError, so the commit doesn't happen.

service._stage_touched (SQLAlchemy Session event, fires on every commit)
↓
8

COMMIT: the commit point

Rows become visible, which makes their chunks searchable and their originals referenced.

service.commit → session.commit (rollback on failure)
↓
9

Settle (after the outermost transaction ends)

Committed: reconcile edited or deleted ids, dropping stale chunks. New files were staged exactly, so they are skipped.
Rolled back: reconcile every touched id (drops the staged chunks; no embedding) and delete uploaded originals no committed row references. Never raises; failures are logged.

service._end_transaction → _settle → indexer.reconcile, _delete_unreferenced

What reconcile does

reconcile(ids) = index_files(ids) + delete_untracked_chunks(ids): it makes the index hold exactly the committed state of those ids, whatever it was before.

  • Missing or deleted file (a rolled-back creation): unindexed through the record manager's keys.
  • Existing file (a rolled-back edit): index(cleanup="incremental") with the committed content. Old chunks are all still there (staging deletes nothing), so they report "skipped" and only the extra staged chunks are deleted. Undo never embeds.
  • Untracked rows: index() writes vectors before records, so a crash between them leaves chunk rows with no record. delete_untracked_chunks removes those.

Because settling looks at the DB's state instead of remembering what happened, a COMMIT whose outcome is unknown (the connection dropped mid-commit) is settled correctly either way.

4. Why staged data is invisible before the commit

Staged thingWhy nobody can see it
Chunks of a new fileSearch scopes to the manifest's committed, active file ids (file_id $in [...]). An uncommitted id is in no scope.
New chunks of an edited fileThe file id is in scope, so search also does read-time validation: a hit is dropped unless its text is still inside lines start_line..end_line of the file's current virtual file. It fetches 2×k rows to make up for drops.
Stale chunks after a failed cleanupSame read-time validation.
S3 originalOnly reachable through a committed row's blob_key (GET /nodes/{id}/raw).

6. Crash leftovers and GC

The undo runs in-process. If the process dies between staging and settling (kill -9, OOM kill, pod eviction, power loss), the undo never runs. Here's what can be left:

LeftoverHarmful?Swept by
Chunks + records of files that never committedNo: unreachable (no file row, so in no search scope)gc_chunks: record-manager groups last written over 1 h ago with no files row
Chunk rows with no record (crash inside index())No: same reasondelete_untracked_chunks, run by reconcile and reindex_all
S3 originals with no rowNo: nothing points at them. They only cost storage.gc_originals: keys under originals/ older than 24 h with no files.blob_key
Stale chunks of a committed editNo: hidden by read-time validationthe next write to the file, or reindex --all
Half-written rowsImpossible: the DB transaction is atomicn/a

Run python scripts/gc.py [--dry-run] any time, e.g. as a daily cron job. The grace periods protect writes still in flight. Soft-deleted rows count as references, so a restore still finds its original. Correctness never depends on GC; it only reclaims space.

7. Edits, deletes and restores

Every write goes through the same seam: service mutations record the ids they touch, and the before_commit event indexes them. That applies to service.commit and to a plain session.commit() alike.

  • PATCH content: only changed chunks are embedded (the record manager skips unchanged ones). After the commit, stale chunks are dropped. On rollback, the new chunks are dropped and the old ones were never touched.
  • Retag / rename: only the body is embedded, so tag changes re-embed nothing.
  • Delete: the file's chunks are unindexed after the commit. The original stays in S3 (the row still references it, for restore).
  • Restore: re-staged before the commit, so the file is searchable as soon as the response returns.

10. Speed: production estimates

These are extrapolations from the measurements above, not measurements. Treat them as ±50%.

The workload is an upload of 100 PDFs × 20 pages (2,000 pages, ~4,500 chunks). The steps run one after another within a request (convert everything, then embed and write in batches of 128, then S3), so their times add up. KB_INGEST_WORKERS is assumed to be set to about the pod's cores ÷ 1.6.

SetupConvertEmbedWriteTotalBottleneck
This Mac (M2 Pro, Ollama on Metal)~4.5 min~3 min~2 min~9–10 minconversion
4 vCPU, no GPU (Ollama on CPU)~4 min8–15 min~2 min~15–20 minembedding
16 vCPU, no GPU~1 min2.5–5 min~2 min~6–8 minembedding
8 vCPU + GPU (L4/A10), Ollama~2 min15–45 s~2 min~4–5 minconversion + write
8 vCPU + GPU, vLLM / TEI~2 min~5 s~2 min~4 minconversion + write
  • A GPU helps only until embedding stops being the slowest step. After that, conversion (CPU of the API pod) and the pgvector write (CPU of Postgres) set the pace.
  • The pgvector write is ~2 min per 4,500 chunks on every setup. Postgres's CPU, not the API's, is what moves it.
  • The OpenShift router timeout is set to 10 min (deploy/openshift/route-timeout.yaml). Uploads that take longer get a 504 at the client, while the server either finishes the write or rolls it back, so it is still all or nothing. Size the timeout, or the upload limits, to your hardware.

11. Concurrent requests

Endpoints are plain defs, so FastAPI runs each request on its own thread (40 by default) with its own session and transaction. Two users don't queue behind each other, but they share the slow resources:

Shared resourceTodayWith vLLM/TEI and enough cores
Embedding serverOllama: one request at a time, so uploads take turnsbatches concurrent requests: parallel up to GPU capacity
Conversion pool4 workers shared by all requestsparallel up to ~cores ÷ 1.6
pgvector writesparallel (one connection each), on Postgres's CPUslikely the next bottleneck: give Postgres cores
DB connections15 (SQLAlchemy default). A write holds one from staging to commit; the 16th waits up to 30 s, then fails (nothing written).raise pool_size
Same file edited twiceserialized by the row lock (by design); the second gives up after the 10 s lock_timeout

Small requests (reads, searches, single edits) stay fast during a big upload, except that with Ollama an edit's embedding waits its turn behind the upload's.

TEI and vLLM are supported through the same code (EMBEDDINGS_MODEL=openai:<model> + EMBEDDINGS_BASE_URL): LangChain's OpenAIEmbeddings with its OpenAI tokenizer turned off, 32 inputs per request. Switching models or servers needs a full re-embed (scripts/reindex.py --all), because the record manager namespace includes the model name. A model that isn't 768-dimensional also needs a migration.

13. Limits and next steps

  • Big uploads run inside the HTTP request. The fix is an async ingest job with a status route: still all or nothing, just outside the request, which removes the router timeout problem.
  • Embedding server: vLLM or TEI on a GPU for parallel, batched embedding (config support not added yet).
  • Faster pgvector writes: a direct bulk insert was about 2× faster than LangChain's path. Other options are a lower HNSW ef_construction (trades some recall), more Postgres CPUs, and splitting writes across a few connections.
  • A hung converter (as opposed to a crashed one) blocks its upload; there's no per-file timeout. A crashed worker is handled: the upload fails with "converter process crashed" and the pool is rebuilt.
  • Deleted files keep their originals in S3 forever (needed for restore). There's no hard-delete/purge yet.
